# Purgu 用户功能对齐设计

## 目标与范围

以 `cleansuperai` 为主工程，补齐 Purgu 当前可用的用户功能、权限、入口和设置。功能验收以用户可见的数据、筛选和选择规则、操作路径、结果及失败反馈为准。保留当前项目所有额外功能。此阶段不做保活、常驻通知、本地推送、后台调度、运营配置和相关埋点。

## 已确定的产品决定

- 沿用当前四个底部入口、Fragment 导航、页面结构与颜色风格；新增快捷入口在首页现有快捷工具区域下方向下排列。
- 采用按功能接入当前架构的方式，不把 Purgu 的 Activity 导航整体搬入。
- 隐私空间行为按 Purgu：导入到应用私有目录并尝试移走原文件；支持恢复到公共图片目录、删除、PIN 与生物识别解锁。应在复制成功且记录成功后才尝试删除源文件，失败要明确显示。
- 当前项目的压缩、联系人、日历、图片增强、测速、重复视频和已有设置保留。

## 功能边界

1. 文件清理：缓存按应用缓存、旧 APK、卸载残留分组；大文件支持 Purgu 的类型、大小、时间筛选和文件详情。Purgu 锁定且无实际扫描内容的展示组不计入清理能力。
2. 媒体清理：图片、视频、音频分类扫描、分组、选择、确认、删除和结果；对齐相似图片、完全重复图片、截图、滑动照片的判定、最佳保留、待删与恢复规则。
3. 工具：应用列表的排序、多选系统卸载；按本月、近 30 天、近 24 小时查看应用移动网络及 Wi-Fi 用量；电池和设备信息。
4. 隐私空间：PIN 设置确认、PIN/生物识别解锁、导入、图库、预览、恢复、删除；按 Purgu 处理会话和返回后重新验证。
5. 入口与设置：首页新增入口向下排列；工具页补齐入口；设置增加小组件与使用条款，保留现有设置；提供小组件添加引导、首页权限提示及退出提示。
6. 共用流程：按功能请求所有文件访问、使用情况访问、媒体及生物识别相关权限；授权返回继续原入口；扫描/删除进度、空状态、取消、失败及报告页使用当前视觉样式。

## 架构

- 新增按能力划分的扫描器与数据模型，扫描在后台执行，结果交给当前 Fragment 页面；可复用现有媒体扫描器，但结果必须满足 Purgu 的分组和选择规则。
- 建立统一 `FeatureRoute` 与权限协调器，记录待执行入口；MainActivity 仍是页面导航宿主。文件访问与 Usage Access 只在对应功能需要时请求。
- 建立删除协调器，区分普通文件、MediaStore 项及系统卸载请求；删除结果只统计确认成功的项。隐私空间导入/恢复单独做事务式文件操作和索引更新。
- 小组件使用独立 Provider 和点击路由，回到当前 MainActivity 的对应功能。

## 分批交付与验收

1. **权限与共用流程**：拒绝、允许、返回设置、进程重建后均能正确恢复入口；扫描和删除不会阻塞主线程。
2. **文件与媒体清理**：使用同一批测试文件对照 Purgu 的候选集、筛选、默认选择、删除数量与剩余文件。
3. **工具与隐私空间**：对照应用排序/卸载、流量范围、电池/设备字段；验证导入、解锁、预览、恢复、删除及中途失败。
4. **入口、设置和小组件**：所有入口可达，新增卡片位于首页快捷区域下方；原有功能和四标签导航仍可用；小组件添加及点击可用。

## 实现风险及处理原则

- Purgu 依赖所有文件访问及使用情况访问；权限未获准时展示说明和可返回状态，不伪造扫描结果。
- Android 媒体删除可能需要系统确认；必须等待确认结果再更新列表和报告。
- 隐私空间导入如果源文件删除失败，明确提示原件仍在设备上；不得把复制成功误称为已移走。
- Purgu 与当前项目的包名、广告位、资源名不同；复用行为与算法，不直接复制其应用标识或运营配置。

## 考虑过的方式

- 整体移植 Purgu Activity：页面还原快，但会产生两套导航和权限流，与保留当前界面结构冲突。
- **按功能接入当前架构（已选）**：在现有导航中补齐能力和入口，统一视觉与权限处理，适合逐批验收。
